# SONYRA Codex Workflow

## Назначение

Этот документ фиксирует, как Codex должен работать на каждом этапе разработки SONYRA Site Manager.

Главный принцип: каждый этап должен быть маленьким, проверяемым и ограниченным явно разрешёнными файлами.

## Preflight перед изменениями

Перед любыми изменениями Codex обязан:

- прочитать текущий запрос этапа;
- определить разрешённые файлы и запрещённые файлы;
- проверить, не требуется ли изменение вне разрешённой области;
- проверить, не требует ли запрос создания scaffold, PHP, JS или CSS до разрешённого этапа;
- проверить существующую структуру проекта;
- проверить наличие применимых инструкций проекта;
- остановиться, если обнаружено STOP-условие.

## Структура каждого Codex-промта

Каждый рабочий промт для Codex должен содержать:

- номер и название этапа;
- цель этапа;
- разрешённые изменения;
- запрещённые изменения;
- точный список файлов, которые можно создать или изменить;
- обязательные правила из rulebook;
- проверки после изменений;
- формат финального отчёта;
- STOP-условия.

Если промт не определяет границы этапа, Codex обязан запросить уточнение или остановиться.

## Разрешённые и запрещённые файлы

Codex может изменять только файлы, прямо разрешённые текущим этапом.

Если этап разрешает только docs/, запрещено создавать или менять:

- PHP-файлы;
- JS-файлы;
- CSS-файлы;
- composer.json;
- package.json;
- WordPress-файлы;
- конфиги окружения;
- assets/;
- includes/;
- templates/;
- scaffold плагина;
- архивы релиза.

## Запрет deploy по умолчанию

Codex не выполняет deploy по умолчанию.

Codex не пишет deploy-скрипты без отдельного явного этапа.

Codex не удаляет старые архивы.

Codex не собирает архив, если текущий этап не является release/package-этапом.

Если этап является release/package-этапом, архив собирается только в ./dist/.

После сборки release/package-этапа Codex обязан показать:

- имя архива;
- размер архива;
- путь к архиву;
- список файлов внутри zip.

Ручная установка zip в WordPress выполняется пользователем.

## Запрет updater-импровизации

Codex не имеет права самовольно писать updater-код, подключать update endpoint, делать HTTP-запросы или менять update-механику, если текущий этап не является явно updater-этапом.

Будущий private updater должен внедряться только отдельной безопасной линией.

До отдельного updater-этапа Codex не подключается к https://updates.dobromap.ru/public/index.php?action=check.

## Запрет database-импровизации

Codex не имеет права создавать таблицы, писать dbDelta или migration runner, если текущий этап не является явно database implementation этапом.

Database schema сначала фиксируется в `docs/SONYRA_DATABASE_SCHEMA.md`.

Database implementation нельзя смешивать с manager UI, REST endpoints, routes, admin pages или wp-admin menu.

## Запрет Auth/OTP-импровизации

Codex не имеет права создавать manager UI, `/manager` route или access screen без учёта `docs/SONYRA_AUTH_OTP_CONTRACT.md`.

Codex не имеет права самовольно заменить OTP-вход на обычный WordPress login.

Codex не имеет права реализовывать Auth/OTP код, если текущий этап не является явно Auth implementation этапом.

## Запрет Auth cookie transport-импровизации

Codex не имеет права ставить или читать auth cookies, если текущий этап не является явно cookie transport implementation этапом.

Codex не имеет права создавать manager access на этапе cookie transport.

Codex не имеет права использовать localStorage/sessionStorage для auth token.

Codex не имеет права разрешать non-HttpOnly auth cookie.

Codex не имеет права делать WordPress login основным входом Пульта сайта.

## Запрет REST auth-импровизации

Codex не имеет права создавать `register_rest_route`, если текущий этап не является явно REST implementation этапом.

Codex не имеет права смешивать REST auth endpoints с UI, `/manager` route, wp-admin menu или manager access.

REST auth endpoints сначала фиксируются в `docs/SONYRA_REST_AUTH_CONTRACT.md`.

REST auth implementation не должен возвращать `session_token`, raw code, raw email или `email_hash` в JSON.

## Сохранение коммерческого названия и бренда

При любом будущем изменении plugin header, about screen, release metadata, diagnostics, manager footer или документации Codex обязан сохранять:

- Plugin Name: Пульт сайта
- Platform: SONYRA Site Platform
- Publisher: SONYRA STUDIO
- Licensor/Seller: ИП Катаев С.А. / IPKTFSA
- Technical name: sonyra-site-manager

Codex не имеет права самовольно переименовывать продукт обратно в SONYRA Site Manager как видимое название плагина.

SONYRA Site Manager остаётся техническим и архитектурным названием базового плагина внутри платформы, но видимое коммерческое название плагина — “Пульт сайта”.

## Запрет импровизации

Codex не должен добавлять архитектуру, зависимости, файлы, директории, менеджеры, runtime, UI, API, REST endpoints или release-артефакты, если они не запрошены текущим этапом.

Запрещено улучшать проект за пределами задачи этапа.

## Запрет смешивать задачи

Один этап должен решать одну группу задач.

Запрещено смешивать:

- документацию и код;
- scaffold и реализацию функций;
- frontend и backend;
- security и visual polish;
- release и разработку;
- миграции и UI;
- разные независимые подсистемы.

## Запрет login-импровизации

Codex не имеет права создавать login UI, route, CSS/JS или manager access, если текущий этап не является явно login implementation этапом.

Codex не имеет права смешивать в одном этапе route foundation, visual shell, REST identifier extension, REST connection, access gate и manager shell.

Codex не имеет права добавлять пароль в login UI первого релиза без отдельного утверждённого этапа.

## Маленькие безопасные этапы

Каждый этап должен завершаться проверяемым состоянием. Если изменение нельзя проверить локально или документально, оно не считается завершённым.

Большие смешанные патчи запрещены.

## Правило остановки при рисках

Codex обязан остановиться, если:

- задача требует выйти за разрешённый список файлов;
- обнаружен конфликт с rulebook;
- проверки не могут быть выполнены;
- результат нельзя подтвердить;
- есть риск переноса старого NDD-кода;
- есть риск использования manager-app.js или manager-v2 как основы;
- требуется решение владельца проекта.

## Финальный отчёт

Каждый этап должен завершаться отчётом:

- что изменено;
- какие файлы созданы или изменены;
- какие файлы не трогались;
- какие правила из rulebook соблюдены;
- какие проверки выполнены;
- есть ли риски;
- какие STOP-условия проверены;
- подтверждение, что старый NDD-код не использован;
- подтверждение, что неправильные варианты названия не используются как рабочие;
- подтверждение, что будущий видимый пользовательский интерфейс должен быть только на русском языке.

## Не продолжать при провале проверок

Если любая обязательная проверка не прошла, Codex обязан:

- не продолжать следующий этап;
- не маскировать ошибку;
- не делать дополнительные изменения без разрешения;
- сообщить точную причину остановки;
- указать файлы и проверки, связанные с проблемой.

## Запрет смешивать Managed Site Agent и Owner Control Plugin

Codex не имеет права создавать центральный Пульт управления сайтами внутри SONYRA Site Manager.

Codex не имеет права смешивать в одном этапе:

- Managed Site Agent API;
- Owner Control Plugin;
- login route;
- visual login shell;
- manager shell;
- billing enforcement;
- remote commands.

Managed Site Agent API можно добавлять только если текущий этап явно относится к PLATFORM/AGENT линии.

Owner Control Plugin должен быть отдельным будущим продуктом, отдельной архитектурной линией и отдельным scaffold/release-процессом. Его нельзя добавлять в SONYRA Site Manager как скрытый модуль, wp-admin page, manager screen или REST controller без отдельного этапа.
